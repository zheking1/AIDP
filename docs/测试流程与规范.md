# Novel OS 项目测试规范与流程

**版本**: 4.0.0  

**来源**: Novel OS 项目实战经验总结  

**适用范围**: 所有项目前端页面功能测试及后端 MCP 工具测试，含所有按钮/链接/点击事件的全面测试

---

## 一、测试理念

### 核心原则

1. **验证真实结果，而非仅检查错误**
   - ❌ 错误做法: 只检查 HTTP 状态码是否为 200
   - ✅ 正确做法: 验证数据是否真的被创建/更新/删除
2. **端到端验证**
   - 前端操作 → API 调用 → 数据库变更 → 前端刷新 → 数据可见
3. **隔离性**
   - 每个测试使用唯一标识的数据
   - 避免测试间的数据干扰
4. **100% 通过率才是真正的完成**

### 三个必须验证

1. **API 成功** — HTTP 200 且无业务错误
2. **数据存在** — 数据库中真的有这条数据
3. **用户可见** — 用户能在页面上看到这条数据

## 二、测试框架与工具

| 组件 | 技术选型 | 说明 |
| --- | --- | --- |
| **E2E 测试框架** | Playwright (`^1.61.1`) | 浏览器自动化测试 |
| **运行环境** | Node.js + Chromium | 支持 headless/headful 模式 |
| **前端测试** | JavaScript (Playwright API) | 页面加载、CRUD、交互验证 |
| **后端测试** | Python 脚本 | 直接调用 MCP API，验证数据库 |
| **数据生成** | `Date.now() + 随机数` | 唯一标识测试数据 |

## 三、测试执行方式（重要）

### 核心原则：浏览器运行在本机，而非服务器上

Playwright E2E 测试的浏览器**始终运行在开发者本机**，直接访问远程服务器的 URL。**不要把测试脚本上传到服务器去跑**（服务器无显示器，看不到浏览器界面）。

```
开发者本机 (Windows/Mac/Linux)         远程服务器 (NAS/Docker)
┌─────────────────────────┐          ┌──────────────────────┐
│  Playwright + Chromium  │  HTTP    │  Web 应用 (SPA)      │
│  (浏览器可见，实时操作)   │ ──────→ │  192.168.0.100:8883│
│                        │          │                      │
│  xxx.js   │  API     │  MCP Server + DB     │
└─────────────────────────┘ ──────→ └──────────────────────┘
```

### 三种运行模式

| 模式 | 配置 | 适用场景 | 能否看到浏览器 |
| --- | --- | --- | --- |
| **可见模式（推荐）** | `headless: false, slowMo: 500` | 调试、开发中验证 | ✅ 能 |
| **无头模式** | `headless: true` | CI/CD、批量回归 | ❌ 不能 |
| **无头+录制** | `headless: true` + `recordVideo` | 自动化 + 事后排查 | ❌ 但可看回放 |

### 执行命令

```bash
# 安装依赖（仅首次）
npm install
npx playwright install chromium

# 执行测试（本机直接运行，浏览器窗口会弹出来）
node tests/scripts/xxx-test.js

# 截图和报告自动保存在本机
# ./test-reports/     - HTML/JSON/Markdown 报告
# ./test-screenshots/ - 失败截图
```

### 前后端测试区分

```
JS 测试脚本（前端 E2E）:
  ├── 运行位置：本机 Windows
  ├── 浏览器：本机 Chromium → 访问远程 URL
  ├── 优点：可见浏览器操作，截图/视频在本机
  └── 命令：node tests/scripts/xxx.js

Python 测试脚本（后端 API）:
  ├── 运行位置：需上传到 NAS 服务器执行
  ├── 方式：pscp 上传 .py 文件 → plink 远程执行
  ├── 优点：直连数据库，可验证数据变更
  └── 命令：pscp + plink 组合（详见下文）
```

## 五、标准测试流程（5 阶段）

### 阶段 1: 页面分析 (Pre-test Analysis)

**目标**: 了解页面的所有操作点和 API 调用

**检查清单**:

- [ ] 扫描所有按钮和交互元素
- [ ] 识别所有表单字段
- [ ] 记录所有 API 调用（使用浏览器 DevTools）
- [ ] 验证工具名格式（必须使用点格式: `tool.name`）
- [ ] 检查 MCP 工具定义（确认参数名和类型）

**输出**: 页面分析报告

---

### 阶段 2: 测试方案 (Test Plan)

**目标**: 为每个操作设计测试用例

**测试用例模板**:

```javascript
{
  "testId": "TC-{page}-{operation}-{number}",
  "page": "页面名称",
  "operation": "CREATE|READ|UPDATE|DELETE|SEARCH|FILTER",
  "description": "测试描述",
  "precondition": ["前置条件"],
  "steps": ["操作步骤"],
  "expected": {
    "apiStatus": 200,
    "dataCreated": true,
    "listRefreshed": true,
    "dataVisible": true
  },
  "testData": {
    "unique": "测试数据-{timestamp}"
  }
}
```

---

### 阶段 3: 执行测试 (Test Execution)

**目标**: 执行测试并监控所有关键指标

**监控 4 项关键指标**:

1. **API 请求**
   - 请求方法 (GET/POST)
   - 请求 URL
   - 请求体参数
   - 工具名是否正确
2. **API 响应**
   - HTTP 状态码
   - 响应体内容
   - 业务错误信息
   - 返回的数据 ID
3. **控制台**
   - JavaScript 错误
   - 警告信息
   - 日志输出
4. **页面状态**
   - 列表刷新
   - 数据可见性
   - 搜索功能

**API 监控代码模板**:

```javascript
page.on('response', async response => {
  const url = response.url();
  if (url.includes('/api/tool')) {
    apiLog.push({
      url,
      status: response.status(),
      body: await response.json().catch(() => null),
      timestamp: new Date().toISOString()
    });
  }
});

page.on('console', msg => {
  if (msg.type() === 'error') {
    consoleErrors.push(msg.text());
  }
});

page.on('pageerror', error => {
  consoleErrors.push(error.message);
});
```

### 阶段 4: 结果验证 (Verification)

**必须验证的检查点**:

| 检查点 | 验证方法 | 通过标准 |
| --- | --- | --- |
| API 调用成功 | 检查响应状态 | `status >= 200 && status < 300 && !body.error` |
| 数据已创建 | 查询数据库或列表 | `list.includes(testData)` |
| 列表已刷新 | 比较列表项数 | `itemsAfter > itemsBefore` |
| 数据可搜索 | 执行搜索 | `searchResults.length >= 1` |

**验证代码模板**:

```javascript
// 1. 记录操作前列表项数
const itemsBefore = await page.$$eval('[data-item-id]', items => items.length);

// 2. 执行操作...

// 3. 验证列表刷新
const itemsAfter = await page.$$eval('[data-item-id]', items => items.length);
const listRefreshed = itemsAfter > itemsBefore;

// 4. 验证数据出现在列表中
const pageText = await page.textContent('#list-container');
const dataVisible = pageText.includes(testData);

// 5. 验证 API 响应
const lastApi = apiLog[apiLog.length - 1];
const apiSuccess = lastApi?.status === 200 && !lastApi?.body?.error;
```

**修复流程**:

5. 验证通过率 100%

## 六、测试类型分级定义

> **核心原则：测试不能只做 API，必须覆盖真实用户操作路径。**

### 6.1 测试分级

| 级别 | 名称 | 测试内容 | 通过标准 |
|------|------|----------|----------|
| **T1** | 冒烟测试 | 页面能打开、HTTP 200、无 JS 错误 | 100% |
| **T2** | 渲染测试 | 数据真正渲染到 DOM，不是空壳 | 100% |
| **T3** | UI 操作测试 | 按钮点击 → 弹窗 → **填写表单** → 提交 → 验证数据出现 | 100% |
| **T4** | 关联管理测试 | 跨实体关联的添加/解绑/验证 | ≥ 90% |

### 6.2 分级说明

**T1 - 冒烟测试**
- 页面 HTTP 200
- 无 JS 控制台错误
- 标题元素存在

**T2 - 渲染测试**
- 列表项数 ≥ 0（或空状态正确显示）
- 第一条数据字段渲染正确
- 统计数字/图表渲染正确
- ❌ 不能只看 HTTP 200 和 HTML 长度
- ❌ 空列表不算通过 — 如果页面应有数据，必须先造数据再验证

**T3 - UI 操作测试（必须填写表单并提交）**
- 每个 `<button>` 必须点击验证
- 每个创建弹窗必须：打开 → 填写所有字段 → 提交 → 验证弹窗关闭 → 验证新数据出现在列表
- 每个编辑弹窗必须：打开 → 验证原始数据回填 → 修改字段 → 提交 → 验证更新
- 每个删除操作必须：点击删除 → 确认 → 验证列表减少
- ❌ 不能只检查"弹窗打开了"就算通过
- ❌ 不能用 API 直调代替 UI 表单操作
- ❌ 不能跳过"数据回显"和"提交后验证"

**T4 - 关联管理测试**
- Agent → 技能/规则/知识库
- 流程 → 步骤规则/技能
- 跨实体添加、解绑、列表更新

## 七、强制测试规则

### 规则 1：每个按钮必须点击测试
页面上每个 `<button>`、`<a href>`、`@click` 元素都必须：
1. 能被找到（selector 有效）
2. 点击后有响应（弹窗/跳转/API 调用）
3. 无控制台错误

### 规则 2：每个创建表单必须填写并提交
创建弹窗测试链：
1. 点击创建按钮 → 弹窗打开
2. 填写所有必填字段（使用唯一测试数据，如 `测试-${Date.now()}`）
3. 填写可选字段（至少填一部分）
4. 点击提交按钮
5. 验证弹窗关闭
6. 验证新数据出现在列表中（页面文本包含测试数据名）
7. 验证无 JS 错误

### 规则 3：每个编辑表单必须回填并提交
编辑弹窗测试链：
1. 点击编辑按钮 → 弹窗打开
2. 验证原始数据已回填到表单字段
3. 修改至少一个字段
4. 点击保存按钮
5. 验证弹窗关闭
6. 验证修改后的数据在列表中可见

### 规则 4：每个删除操作必须确认并验证
删除测试链：
1. 点击删除按钮 → 确认弹窗出现
2. 确认删除
3. 验证列表项减少
4. 验证被删数据不再可见

### 规则 5：空页面必须先造数据
如果页面列表为空（如搜索页、图谱页、质量检查页），必须：
1. 先通过 UI 创建测试数据
2. 再执行该页面的功能测试
3. 禁止以"页面无数据"作为跳过测试的理由

### 规则 6：UI 测试不能跳过表单
任何有 Create/Edit 功能的页面，必须通过 Playwright 真实填写表单并点击保存，
禁止仅用 API 验证后端。

### 规则 7：列表页必须验证数据渲染
页面加载后必须检查：
- 列表项数 ≥ 0（不是空列表）
- 第一条数据的标题/字段可见
- 点击任意项能打开详情

## 九、测试执行流程

### 当前流程（有问题）
```
1. 页面加载 → 只查 HTTP 200        ❌ 浅层
2. API CRUD → 直接调 API，不走 UI   ❌ 跳过前端
3. 汇总报告
```

### 修正后流程（必须遵循）
```
1. 页面加载 → HTTP 200 + 列表数据渲染验证           ✅ T1+T2
2. 空页面造数据 → 通过 UI 创建测试数据              ✅ T2前置
3. 按钮冒烟 → 逐个点击页面所有按钮，验证响应        ✅ T3(冒烟)
4. 创建测试 → 填写表单 → 提交 → 验证数据出现       ✅ T3(创建)
5. 编辑测试 → 回填验证 → 修改 → 提交 → 验证更新    ✅ T3(编辑)
6. 删除测试 → 确认删除 → 验证列表减少              ✅ T3(删除)
7. 关联测试 → 验证跨实体管理                        ✅ T4
8. 汇总报告（按 T1/T2/T3/T4 分层统计）             ✅
```

### 禁止的测试方式
| ❌ 禁止 | ✅ 正确做法 |
|---------|------------|
| 只检查弹窗是否打开 | 填写表单并提交 |
| 用 `page.evaluate(fetch())` 代替 UI 操作 | 用 Playwright 填写 input、点击 button |
| 空页面直接跳过 | 先创建测试数据 |
| 只测"查看"不测"编辑" | 查看和编辑都要测 |
| 只测 API 返回 200 | 验证数据出现在页面上 |

### 完整表单测试示例（以全局规则为例）

```javascript
// ❌ 错误：只检查弹窗打开
const btn = await page.$('button:has-text("创建")');
await btn.click();
const modal = await page.$('h2:has-text("创建全局规则")');
record('弹窗打开', !!modal);  // 这不是完整测试！

// ✅ 正确：填写表单 → 提交 → 验证结果
// 1. 打开弹窗
await page.click('button:has-text("创建")');
await page.waitForSelector('h2:has-text("创建全局规则")');

// 2. 填写所有字段
const uniqueName = `测试规则-${Date.now()}`;
await page.fill('input[x-model="form.name"]', uniqueName);
await page.fill('textarea[x-model="form.content"]', '自动化测试内容');
await page.fill('textarea[x-model="form.description"]', '测试描述');
await page.selectOption('select[x-model="form.category"]', 'security');
await page.selectOption('select[x-model="form.severity"]', 'high');

// 3. 提交
await page.click('button:has-text("创建"):not([class*="indigo-600"])');
// 或更精确：找到弹窗内的提交按钮
const submitBtn = await page.$('button[\\@click="createRule()"]');
await submitBtn.click();

// 4. 验证弹窗关闭
await page.waitForTimeout(1000);
const modalGone = !(await page.$('h2:has-text("创建全局规则")'));
record('弹窗关闭', modalGone);

// 5. 验证新数据出现在列表
const pageText = await page.textContent('body');
record('数据可见', pageText.includes(uniqueName));
```

## 十一、交互元素全面测试（按钮 / 超链接 / 点击事件）

> **核心原则：页面上每一个可点击的元素都必须经过测试，不能遗漏任何一个按钮或链接。**

### 6.1 按钮分类测试矩阵

| 按钮类型 | 测试重点 | 预期结果 |
|----------|----------|----------|
| **创建类** | 点击打开表单/弹窗 → 填写数据 → 保存 | API 200 + 列表刷新 + 数据可见 |
| **编辑类** | 点击打开编辑弹窗 → 数据回显 → 修改保存 | 原始数据正确填充 + 修改后更新可见 |
| **删除类** | 点击删除 → 确认对话框 → 确认删除 | API 200 + 列表项减少 + 数据消失 |
| **查看/详情类** | 点击查看 → 弹窗/页面展示详情 | 数据完整展示，字段与数据库一致 |
| **导航/跳转类** | 点击超链接/Tab/菜单项 | 正确跳转或加载目标页面，无 404 |

## 十四、常见陷阱与经验教训

### ❌ 教训 1: 打开弹窗不等于完成测试

**问题**: 测试脚本点击了"新建"按钮打开弹窗，但没有点击保存/提交按钮。

**后果**: 测试显示"成功"但实际上数据从未被创建。

**修复方案**:

```javascript
// ❌ 错误：只打开弹窗
await page.click('button:has-text("新建")');
// 没有后续操作...测试结束

// ✅ 正确：完整操作链
await page.click('button:has-text("新建")');
await page.fill('#title', '测试数据');
await page.click('button[type="submit"]');
await page.waitForTimeout(2000);
// 验证 API 调用结果
const lastApi = apiLog[apiLog.length - 1];
assert(lastApi.status === 200);
assert(!lastApi.body.error);
```

---

### ❌ 教训 2: API 成功 ≠ 数据可见

**问题**: API 返回 200 OK 后，没有验证数据是否真的出现在前端列表中。

**后果**: 测试显示通过但实际上列表没有刷新，用户看不到新数据。

**常见原因**:

1. API 返回成功但数据被后端过滤（权限、状态等）
2. 前端没有调用刷新列表的 API
3. 列表有分页，数据在另一页
4. 前端使用本地缓存，没有实时更新

**修复方案**:

```javascript
// API 200 后必须继续验证：
const createApi = apiLog[apiLog.length - 1];
assert(createApi.status === 200);
assert(!createApi.body.error);

// 1. 等待列表刷新
await page.waitForTimeout(2000);

// 2. 验证列表项数变化
const itemsAfter = await getItemsCount(page);
assert(itemsAfter > itemsBefore, `列表未刷新: ${itemsBefore}→${itemsAfter}`);

// 3. 验证数据文本可见
const pageText = await page.textContent('#list-container');
assert(pageText.includes(testData), `数据未出现在列表中: ${testData}`);

// 4. 如果数据不在第一页，尝试分页切换
if (!pageText.includes(testData)) {
  const nextPageBtn = await page.$('.pagination-next, button:has-text("下一页")');
  if (nextPageBtn) {
    await nextPageBtn.click();
    await page.waitForTimeout(1000);
    const page2Text = await page.textContent('#list-container');
    assert(page2Text.includes(testData), '数据在分页后仍不可见');
  }
}
```

---

### ❌ 教训 3: 列表刷新导致元素脱离 DOM

**问题**: 删除/编辑操作后，列表刷新会导致之前找到的 DOM 元素引用失效。

**后果**: 点击删除按钮后，按钮元素从 DOM 中移除，后续操作报错 `Element is not attached to the DOM`。

**修复方案**:

```javascript
// ❌ 错误：引用会失效
const deleteBtn = await page.$('button[onclick*="delete"]');
await deleteBtn.click();
// 列表刷新后，deleteBtn 引用已失效

// ✅ 正确：操作后立即验证，不保留引用
const itemsBefore = await page.$$eval('.item', items => items.length);

const deleteBtn = await page.$('button[onclick*="delete"]');
await deleteBtn.click();

page.once('dialog', async dialog => {
  await dialog.accept();
  await page.waitForTimeout(2000);
  // 使用新查询，不依赖旧引用
  const itemsAfter = await page.$$eval('.item', items => items.length);
  assert(itemsAfter < itemsBefore, '删除后列表项数未减少');
});
```

### ❌ 教训 7: 搜索可能用本地过滤而非 API 调用

**问题**: 输入搜索关键词后，页面前端可能直接用 JS 过滤已有数据，不会触发新的 API 请求。

**后果**: 测试检查 API 调用次数为 0，误判搜索功能异常。

**修复方案**:

```javascript
async function testSearch(page, testData) {
  const searchInput = await page.$('#search-input');
  if (!searchInput) return 'N/A';

  // 记录搜索前状态
  const beforeText = await page.textContent('#list-container');
  const beforeItems = await page.$$eval('.item', items => items.length);

  // 输入搜索词
  await searchInput.fill(testData.substring(0, 10));
  await page.waitForTimeout(1000);

  // 验证方法1：检查列表是否过滤
  const afterItems = await page.$$eval('.item', items => items.length);
  const searchWorks = afterItems < beforeItems || afterItems === 0;

  // 验证方法2：检查是否出现"无结果"提示
  const afterText = await page.textContent('#list-container');
  const noResult = afterText.includes('暂无') || afterText.includes('未找到');

  assert(searchWorks || noResult, '搜索可能未生效');

  // 清空搜索，恢复列表
  await searchInput.fill('');
  await page.waitForTimeout(1000);
}
```

### ❌ 教训 8: 按钮点击可能打开新模态框而非直接操作

```javascript
      await this.page.waitForTimeout(1000);
    }

      '#project-select option',

    );

      await this.page.waitForTimeout(1000);
```

## 十七、后端 MCP 测试要点 (Python)

### MCP 工具命名规则

- 工具名使用**点格式**: `prompt.template.upsert`（非 `prompt_template_upsert`）
- API 客户端方法使用 **camelCase**: `promptTemplate.create()`

### Delete 工具模式

Delete 工具必须返回 dict，不能返回 bool（FastMCP 约束）:

```python
# ❌ 错误 - 返回 bool
return await service.delete(project_id, key)

# ✅ 正确 - 包装在 dict 中
deleted = await service.delete(project_id, key)
return {"ok": deleted, "key": key}
```

### 禁止使用 @validate_call

`@validate_call` 装饰器在代码库中不存在：

```python
# ❌ 错误
@validate_call
@mcp.tool(name="user.update")
async def user_update(username: str, ...): ...

# ✅ 正确
@mcp.tool(name="user.update")
async def user_update(username: str, ...):
    validate_required(locals(), "username")
```

### 数据库外键约束

所有引用 `users` 表的 FK 必须指定 ON DELETE 行为：

```sql
-- 日志/审计表：删除用户时级联删除
ALTER TABLE log_table ADD CONSTRAINT fkey
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE;

-- 配置表：删除用户时置 NULL
ALTER TABLE config_table ADD CONSTRAINT fkey
  FOREIGN KEY (updated_by) REFERENCES users(id) ON DELETE SET NULL;
```

### MCP 工具返回值规范

- 必须返回 dict 或 None（FastMCP 约束）
- 不能返回 bool、str、list 等非 dict 类型

## 二十一、MCP 认证故障排除

### 症状

```
User not found: web-service
Invalid or expired API token
```

### 修复步骤

1. 创建系统用户:
   ```sql
   INSERT INTO users (username, status, is_admin) 
   VALUES ('web-service', 'active', true)
   ON CONFLICT (username) DO UPDATE SET status = 'active';
   ```
2. 创建 API Token:
   ```sql
   INSERT INTO api_tokens (user_id, token_hash, scopes)
   SELECT id, 'SHA256_HASH', ARRAY['admin','read','write']
   FROM users WHERE username = 'web-service';
   ```
3. 验证环境变量:
   ```bash
   docker exec novel-os-web env | grep MCP_SERVICE_TOKEN
   ```

## 二十二、AIDP Controller WebUI 测试关键发现

### Alpine.js CDN 问题

AIDP 使用 Alpine.js 作为前端交互框架。在代理环境下，CDN (`cdn.jsdelivr.net`) 可能被屏蔽，导致 Alpine.js 无法加载，所有 `@click`/`x-model` 交互失效。

**解决方案**: 下载 Alpine.js 到 `apps/controller/app/web/static/vendor/alpine.min.js`，更新所有布局模板引用本地文件。

已更新的布局文件:
- `layouts/base.html`
- `layouts/embed.html`
- `layouts/unified_base.html`
- `layouts/workspace.html`
- `admin/models-frame.html`, `roles-frame.html`, `settings-frame.html`, `users-frame.html`
- `auth/api-keys-frame.html`, `profile-frame.html`
- `pages/tools-frame.html`

### Workspace SPA 架构

AIDP Controller 使用 SPA 架构:
- `workspace.html` 是主布局，包含侧边栏和标签页系统
- 各功能页面（规则/技能/知识库等）是 HTML 片段，通过 AJAX `?partial=1` 加载
- 片段中的 `x-data` 属性会被 workspace 的 JS 替换为 `data-alpine-component`，然后调用 `Alpine.initTree()` 初始化

**关键发现**: 直接访问 `/rules/global` 等 URL 会渲染原始 HTML 片段（无 Alpine.js 库），导致所有交互失效。**必须通过 workspace 的 `openTab()` 方法加载页面**。

### 正确的测试方法

```javascript
// 1. 登录并进入 workspace
await pg.goto(`${BASE_URL}/login`, ...);
await login(pg);
await pg.goto(`${BASE_URL}/`, { waitUntil: 'networkidle' });
await pg.waitForTimeout(5000);

// 2. 通过 workspace.openTab() 加载页面
await pg.evaluate(() => {
  const ws = Alpine.$data(document.querySelector('[x-data="workspace()"]'));
  ws.openTab('rules-global', '全局规则', 'fas fa-gavel', '/rules/global');
});
await pg.waitForTimeout(5000);

// 3. 通过 Alpine.$data() 操作组件
await pg.evaluate(() => {
  const d = Alpine.$data(document.querySelector('[x-data="globalRulesPage()"]'));
  d.showCreateModal = true;
  d.form.name = 'test-rule';
  d.form.content = 'test content';
  d.createRule();
});
await pg.waitForTimeout(3000);

// 4. 验证结果
const result = await pg.evaluate(() => {
  const d = Alpine.$data(document.querySelector('[x-data="globalRulesPage()"]'));
  return d.rules?.some(r => r.name === 'test-rule');
});
```
